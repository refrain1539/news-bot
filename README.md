# news-bot

毎朝7:10 JST(GitHub Actionsの仕様上、数十分遅延することがあります)に日本語のニュースを
取得し、世間の重要度でランキングして、総合ニュース10本・テック/科学ニュース4本を
Discordに2通(embed)で届けるBotです。テレビを見なくなった分の代替として、朝に
ざっと世の中の動きを把握するためのものです。

**要約を読んで済ませる前提の設計です。** リンク先の記事まで開くことは稀という
運用に合わせて、`require_lead: true` により「要約を作れるトピックだけ」を通知し、
その中から世間の重要度が高いものを選びます。重要でも要約の材料(RSSのリード文)が
取れないトピックは、見出しだけ並べても読まれないため通知しません。

天気予報機能も追加されており、ニュースより先に今日と明日の時間帯別天気を1通
届けます。そのため毎朝の通知は合計**3通**(天気 / 総合ニュース / テック・科学
ニュース)になります。詳細は下記の「天気予報」の節を参照してください。

金銭コストはかかりません。GitHub Actions無料枠 + Gemini API無料枠のみで動作し、
有料APIは一切使いません。

## 仕組み(パイプライン)

`src/main.py` が以下の順に実行します。**各段は失敗しても後続を止めません**(はてブが
取れなくても、Geminiが落ちていても、見出しとリンクだけの通知には価値があるため)。
唯一の例外は、全フィードが1件も取れなかった場合で、この場合だけ通知する中身が無いため
早期終了します。

0. **weather** (`main.py` の `run_weather` → `weather.py`) — 今日と明日の時間帯別
   天気を取得し、ニュースより先に1通送る。天気とニュースは互いに独立しており、
   この段が失敗してもニュースの取得・通知は続行する。
1. **fetch** (`fetch_feeds.py` + `article_cache.py`) — `config.yml` の `sources` を
   順に取得し、記事を `Article` に正規化する。1ソースの取得・パース失敗は握りつぶして
   次のソースへ進む。取得した当日ぶんに、**3時間おきに貯めておいた蓄積**
   (`data/article_cache.jsonl`)を合わせて候補にする。詳細は下記「記事の蓄積」を参照。
2. **cluster** (`cluster.py`) — 同じ話題を報じた記事を見出しの類似度で名寄せし、
   `Cluster`(1トピック)にまとめる。
3. **hatena** (`main.py` の `attach_hatena_counts` → `hatena_count.py`) — 各トピックの
   はてなブックマーク件数を取得する。失敗しても0件として続行する。
4. **rank** (`rank.py`) — レーン(総合/テック)ごとに独立してスコアを計算し、既報と
   (`require_lead: true` なら)リード文が取れないトピックを除いて `min_score` で
   足切りし、`quota` 件を選抜する。
5. **summarize** (`summarize.py`) — 選抜されたトピックのうちリード文を持つものだけを
   Geminiに1リクエストでまとめて要約させる。`require_lead: true` のときは、
   リード文があったのにGeminiが要約を返さなかったトピックを `main.py` が通知から
   落とす。ただし要約が1件も作れなかったとき(APIキー未設定・Gemini障害)は
   全件を落とすと無音になるため、そのままの内容で通知する。
6. **notify** (`notify_discord.py`) — レーンごとに1メッセージ(1 embed)でDiscordに投稿する。

最後に、通知が1件でも成功していれば `data/seen_urls.json` に既報URLを記録します。

## 天気予報

ニュースとは別に、毎朝ニュースより先に天気予報を1通(embed)送ります。今日と明日の
2日ぶんを、tenki.jpと同じ8つの時間帯区分(未明/明け方/朝/昼前/昼過ぎ/夕方/夜のはじめ/
夜遅く)で表示します。各区分には1時間ずつ3つの天気絵文字と気温レンジが出ます。
降水確率はその区分内の最大値が `pop_alert_threshold`(既定50)以上のときだけ、
☔付きで表示されます。表示例(2026-09-01の実データ、今日ぶん):

```
**今日 09/01(火)**　最高35℃ / 最低27℃　🌅05:29 🌇18:24
`未明　　　` 🌤️🌤️🌤️　26〜26℃
`明け方　　` 🌤️🌤️🌦️　25〜26℃
`朝　　　　` 🌦️🌦️🌦️　26〜26℃
`昼前　　　` ⛅🌦️🌦️　27〜28℃　☔92%
`昼過ぎ　　` 🌦️🌦️🌦️　29〜31℃　☔97%
`夕方　　　` 🌤️🌤️🌤️　29〜30℃　☔99%
`夜のはじめ` 🌤️⛅🌤️　27〜28℃　☔82%
`夜遅く　　` 🌤️☀️☀️　26〜27℃
```

### 情報源

情報源は2つで、どちらもAPIキー不要・無料です。そのため天気機能の追加にあたって
**新しいGitHub Secretsの追加は不要**です。

- **Open-Meteo**(`api.open-meteo.com`) — 毎時の天気コード・降水確率・降水量・
  湿度・風向風速。48時間分を取得する。
- **気象庁 公式JSON**(`www.jma.go.jp/bosai/forecast/data/forecast/260000.json`) —
  日最高/最低気温。地点補正済み。

なお **tenki.jpはスクレイピングしていません**(利用規約と著作権のため)。参考に
したのは表示形式(8区分・1〜24時表記)だけです。

### 気温を二段で持っている理由

`src/models.py` の `DayForecast` 周辺に詳しい経緯のコメントがあります。要約すると
以下のとおりです。

- 2026-09-01の実測で、京都の今日の最高気温は気象庁35℃ / tenki.jp 33.8℃ /
  Open-Meteo 30.3℃でした。Open-Meteoは公式より3〜5℃低く出ます。
- 原因は標高差ではありません(京都地方気象台41mと左京区側69mでは0.4℃しか
  動きません)。京都盆地特有の日中高温を、Open-Meteoの格子モデルが捉えきれない
  ことが原因です。
- 毎時カーブを線形リスケールして日最高/最低を気象庁の値に合わせる補正を実装して
  試しましたが、格子モデルの振幅5.5℃を公式の10℃に引き伸ばすと係数が1.8倍になり、
  夕方が34〜36℃に張り付く非現実的な結果になったため**採用しませんでした**。
- そのため補正はせず、**見出しの最高/最低は気象庁の値、時間帯行の気温は
  Open-Meteoの参考値**として分けて表示しています。embedのfooterにも
  「毎時の気温はOpen-Meteoの参考値 / 最高・最低は気象庁の地点予報」と明記して
  います。
- **結果として、見出しの最低気温と時間帯行の気温が数℃食い違って見えることが
  あります**(実測例: 見出し「最低27℃」に対し時間帯行は25℃)。これは仕様であり、
  footerの注記で担保しています。
- 気温の精度を優先したい場合は、`weather.enabled: false` にして天気機能自体を
  止め、気象庁の日最高/最低だけを別途確認する、という選択もあります。

### 座標について

`weather.latitude` / `weather.longitude` には**京都地方気象台**(35.0117,
135.7320)を使っています。左京区は北部が山地で市街地の気温から外れるため、
意図的に市街地側の地点を採っています。座標を動かす場合はこの点に注意してください。

### ニュースとの独立性

天気とニュースは互いに独立しています。天気の取得元(Open-Meteo・気象庁)が
落ちていてもニュースは届き、ニュースが0件でも天気は届きます。`main.py` の
`run_weather` はここで発生した例外をすべて握りつぶし、ログに残すだけにしています。

### 無効化

`weather.enabled: false` にすると、天気の取得・通知だけを丸ごと止められます
(ニュースの通知には影響しません)。

### 採用しなかったソースと理由

将来「NHKを足そう」のように再検討したくなったときに再調査しなくて済むよう、
`config.yml` に記録してあるものをここにも残します。

- **NHK公式RSS**(`www3.nhk.or.jp/rss/news/cat*.xml`) — 2026-08-30時点で全カテゴリの
  最新記事が3週間前で止まっており、更新が停止している。
- **EurekAlert日本語版**(`jp.eurekalert.org/rss.xml`) — 配信停止。itemが0件。
- **Googleニュース SCIENCEセクション** — 最新記事が4日前で、日次の新着ボットには
  鮮度が足りない。
- **NewsAPI.org** — 無料枠は24時間遅延かつ開発用途限定で、新着通知に使えない。
- **各社サイトのスクレイピング** — 利用規約と著作権の両面でリスクがあるため不採用。

## どうやって「おすすめ」を決めているか

このBotは自分の興味では選びません。Yahoo!トピックス・livedoorトピックス・時事通信
ランキングという**既に人間が付けた重要度**と、報道媒体数・はてなブックマーク件数という
**外形的な指標**だけでスコアを付けます(`rank.py` の `score_cluster`)。

```
score = Σ(signal を持てば加点)
      + outlet_count の重み × (報じた媒体数 - 1)
      + hatena の重み × log10(はてなブックマーク数 + 1)
```

### レーン(総合/テック・科学)を分けている理由

**スコアはレーン内でしか比較しません。** 総合レーンとテックレーンを1つのプールに
混ぜると、`curated_yahoo` / `curated_livedoor` の項が定義上いつも0になるテック記事は
構造的に1本も選ばれなくなります(そもそもYahoo!トピックス・livedoorトピックスに
テック専用のキュレーションが存在しないため)。そのため `config.yml` で `quota` を
レーンごとに固定で分けており、`rank_and_select()` もレーンごとに独立して候補を集め・
足切りし・並べ替えています。この前提を壊す実装(全レーンを1つのリストにまとめてから
まとめて上位N件を採る、など)はしないでください。

## 名寄せについて

同じ話題を複数媒体が報じたとき、見出しを正規化して文字bigram集合を作り、
**Jaccard係数ではなく重なり係数(Szymkiewicz-Simpson, `|A∩B| / min(|A|,|B|)`)**
で類似度を測っています(`src/cluster.py` の `overlap_coefficient()`)。

理由は見出しの長さの構造的な違いです。Yahoo!トピックスの見出しは13〜16字に固定
されている(いわゆる13文字ルール)のに対し、朝日新聞やITmediaの見出しは23〜54字
あります。Jaccardは分母が和集合なので、短い見出しはどれだけ内容が一致していても
構造的に高いスコアを出せません。2026-08-31の実データでは、正解ペア(同一話題)の
重なり係数が0.385〜0.857だったのに対し、無関係なペアの最大は0.214で、閾値0.35は
その間に十分な余裕を持って収まっています。詳しい経緯は `src/cluster.py` の
`overlap_coefficient()` のコメントを参照してください。

### 既知の限界

この指標を使っても誤マッチは残ります。同日の実データで16件のクラスタにまとまった
うち2件が誤マッチでした。誤マッチのペアは正解ペアと数値上分離できません
(誤マッチ側が0.385・0.533、正解側が0.385・0.500という具合に、閾値調整では
分離できない領域で重なっています)。実害は `outlet_count` が1つ増えてスコアが
少し上がることに限られます。代表記事と要約はどちらも同じ記事(代表記事)から
取るため、見出しと要約の内容が食い違うことはありません。

## 設定の変え方

`config.yml` がユーザーが編集する唯一のファイルです。よく触る項目は以下のとおりです。

| 項目 | 変えると何が起きるか |
|---|---|
| `lanes[].quota` | そのレーンから通知する最大本数が変わる |
| `lanes[].weights` | スコアの重み。ある項目を上げるとその要素が強く効き、選ばれやすくなる |
| `lanes[].min_score` | この点数未満のトピックは、枠が余っていても通知されなくなる |
| `lookback_hours` | 何時間前までに配信された記事を取得対象にするか |
| `cluster_threshold` | 名寄せの閾値。上げると同一話題としてまとまりにくくなり、下げると無関係な話題まで1つにまとめられるリスクが上がる |
| `summary_max_chars` | 要約の目安文字数(実際の上限はこの1.5倍。超えると末尾を切り詰めて`…`を付ける) |
| `spill_over` | あるレーンでquotaが埋まらなかったとき、余った枠をもう一方のレーンの次点で埋めるか |
| `require_lead` | `true` なら、要約を作れない(リード文が取れない)トピックをスコアに関係なく通知しない。`false` にすると要約の有無は同点時の優先順位にしか影響しなくなる |
| `weather.enabled` | `false` にすると天気の取得・通知を丸ごとスキップする |
| `weather.label` | 通知の見出しに出す地点名 |
| `weather.latitude` / `weather.longitude` | Open-Meteoに渡す座標(既定は京都地方気象台) |
| `weather.jma_area_code` / `weather.jma_point_name` | 気象庁の予報区コードと地点名 |
| `weather.days` | 天気を何日ぶん通知するか(1で今日のみ、2で今日と明日) |
| `weather.pop_alert_threshold` | 時間帯ブロックの最大降水確率がこの値以上のときだけ☔を出す |

調整例: 総合レーンの通知がYahoo!トピックス採用記事に寄りすぎると感じたら、
`lanes: general` の `weights.curated_yahoo` を `3.0` から下げてください。

## 記事の蓄積

RSSは「直近N件」のスライディングウィンドウで、**1回の取得で見えるのは数時間分
しかありません**。2026-09-01 の実測値です。

| ソース | 件数 | カバーしている時間 |
|---|---|---|
| Yahoo!トピックス | 8 | **1.9時間分** |
| Yahoo!ニュース エンタメ | 50 | 1.6時間分 |
| Yahoo!ニュース 経済 | 50 | 4.1時間分 |
| Yahoo!ニュース 国内 | 50 | 5.5時間分 |
| Googleニュース 総合 | 30 | 16.2時間分 |
| 朝日新聞 | 37 | 57.0時間分 |

朝1回だけ実行すると、`lookback_hours: 30` で前日ぶんを見ているつもりでも、
実際にフィードが供給しているのは数時間分だけです。特に**スコアの最大の重み(3.0)を
持つYahoo!トピックスが1.9時間分(8件)しか見えず**、その日の主要ニュースの2割弱しか
候補にできていませんでした。「住宅ローン変動金利 2行引き上げ」が要約なしで通知された
のも、発表から数時間で経済カテゴリの窓から流れ、リード文を持つ記事を拾えなかった
ためです。名寄せの失敗ではありません(Googleニュース側とは重なり係数0.846で
きちんと一致していました)。

そこで `.github/workflows/collect.yml` が**3時間おきに記事だけを集めて**
`data/article_cache.jsonl` に貯め、朝の本番実行がその蓄積と当日ぶんを合わせて
処理します。**収集は通知も要約もしません**(Gemini・DiscordのSecretsも渡していません)。
Publicリポジトリなので GitHub Actions の実行時間は無料無制限で、追加コストはゼロです。

- 形式は **JSON Lines**(1行1記事)。`published` の昇順で書き出すので、3時間おきの
  更新でも git の差分が「末尾への追加 + 先頭からの削除」に収まり、履歴が膨らみにくい。
- `cache_ttl_hours`(36時間)より古い記事は保存時に捨てる。`lookback_hours`(30)より
  長くしてあるのは、まだ通知対象の時間帯にある記事をキャッシュから消さないため。
- `published` を持たない記事はキャッシュに載せない(TTLの判定ができないため)。
  日付を持たない記事は毎回の取得ぶんからそのまま流れ込む。
- 記事が1件も取れなかった実行では保存しない(既存の蓄積を空で上書きしないため)。
- 書き込みは一時ファイル → `os.replace` で差し替える(途中で落ちてもファイルが壊れない)。
- `collect.yml` と `daily.yml` はどちらも `data/` にcommitするため、push前に
  `git pull --rebase origin main` を挟んでいる。

## 状態ファイル

`data/seen_urls.json` は、一度通知したトピックのURLを記録し、`config.yml` の
`seen_ttl_days`(14日間)は再通知を抑制するためのファイルです。クラスタ内の
全URL(代表記事だけでなく)を記録するので、代表記事が日によって入れ替わっても
再通知されません。

**同じ日に2回実行すると、2回目はほぼ空(または大幅に件数が減った状態)になります。**
これは不具合ではなく、1回目の実行で通知した記事のURLが既報として記録されるためです。
GitHub Actions側は本番実行(dry_runでない)のあとに `data/seen_urls.json` を
自動でcommit・pushします(`.github/workflows/daily.yml` の最終ステップ)。

## 著作権・利用規約について

- RSSのリード文をそのまま貼らず、Geminiに言い換えさせてから通知しています
  (`summarize.py` のプロンプトでコピー&ペーストを明示的に禁止している)。
- 記事本文は取得していません(取得しているのはRSSのタイトルとリード文のみ)。
- 通知には必ず元記事へのリンクを付けています。
- Googleニュースのフィードはcopyright表記で用途をpersonal・non-commercialに
  限定しています。個人のDiscordサーバーへの通知はこの範囲ですが、この内容を
  Webサイトなどへ転載することはできません。

## 定期実行の有効化

`.github/workflows/daily.yml` の `cron` はコメントアウトされた状態で置いてあります。
`workflow_dispatch` の手動実行(`dry_run: true` → `dry_run: false` の順)でDiscordへの
実際の投稿まで確認してから、コメントを外して定期実行を有効にしてください。
