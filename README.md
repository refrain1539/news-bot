# news-bot

毎朝7:00 JST(GitHub Actionsの仕様上、数十分遅延することがあります)に日本語のニュースを
取得し、世間の重要度でランキングして、総合ニュース6本・テック/科学ニュース4本を
Discordに2通(embed)で届けるBotです。テレビを見なくなった分の代替として、朝に
ざっと世の中の動きを把握するためのものです。

金銭コストはかかりません。GitHub Actions無料枠 + Gemini API無料枠のみで動作し、
有料APIは一切使いません。

## 仕組み(パイプライン)

`src/main.py` が以下の順に実行します。**各段は失敗しても後続を止めません**(はてブが
取れなくても、Geminiが落ちていても、見出しとリンクだけの通知には価値があるため)。
唯一の例外は、全フィードが1件も取れなかった場合で、この場合だけ通知する中身が無いため
早期終了します。

1. **fetch** (`fetch_feeds.py`) — `config.yml` の `sources` を順に取得し、記事を
   `Article` に正規化する。1ソースの取得・パース失敗は握りつぶして次のソースへ進む。
2. **cluster** (`cluster.py`) — 同じ話題を報じた記事を見出しの類似度で名寄せし、
   `Cluster`(1トピック)にまとめる。
3. **hatena** (`main.py` の `attach_hatena_counts` → `hatena_count.py`) — 各トピックの
   はてなブックマーク件数を取得する。失敗しても0件として続行する。
4. **rank** (`rank.py`) — レーン(総合/テック)ごとに独立してスコアを計算し、既報を除いて
   `min_score` で足切りし、`quota` 件を選抜する。
5. **summarize** (`summarize.py`) — 選抜されたトピックのうちリード文を持つものだけを
   Geminiに1リクエストでまとめて要約させる。
6. **notify** (`notify_discord.py`) — レーンごとに1メッセージ(1 embed)でDiscordに投稿する。

最後に、通知が1件でも成功していれば `data/seen_urls.json` に既報URLを記録します。

## ニュースソース一覧

| ソース | レーン | 役割 |
|---|---|---|
| Yahoo!トピックス (`yahoo_topics`) | 総合 | `curated_yahoo` シグナル(人手キュレーション採用)。見出しのみでリード文を持たないため、名寄せした他社記事からリード文を借りる |
| livedoorトピックス (`livedoor_topics`) | 総合 | `curated_livedoor` シグナル(人手キュレーション採用) |
| 朝日新聞 (`asahi`) | 総合 | シグナル無し。媒体数カウントと、要約の材料になるリード文の提供が主な役割 |
| 時事通信ランキング (`jiji_ranking`) | 総合 | `jiji_ranking` シグナル(ランキング入り) |
| Googleニュース 総合 (`google_top`) | 総合 | シグナル無し。`representative_ok: false` のため通知の代表記事には選ばれず、名寄せと媒体数カウントのみに使う |
| ITmedia (`itmedia`) | テック | シグナル無し。見出し先頭の `[ITmedia News]` のような角括弧を除去(`strip_bracket_prefix`)してから使う |
| Impress Watch (`impress`) | テック | シグナル無し |
| GIGAZINE (`gigazine`) | テック | シグナル無し |
| Googleニュース TECHNOLOGY (`google_tech`) | テック | シグナル無し。`representative_ok: false` |

### 採用しなかったソースと理由

将来「NHKを足そう」のように再検討したくなったときに再調査しなくて済むよう、
`config.yml` に記録してあるものをここにも残します。

- **NHK公式RSS**(`www3.nhk.or.jp/rss/news/cat*.xml`) — 2026-08-30時点で全カテゴリの
  最新記事が3週間前で止まっており、更新が停止している。
- **EurekAlert日本語版**(`jp.eurekalert.org/rss.xml`) — 配信停止。itemが0件。
- **Googleニュース SCIENCEセクション** — 最新記事が4日前で、日次の新着ボットには
  鮮度が足りない。
- **NewsAPI.org** — 無料枠は24時間遅延かつ開発用途限定で、新着通知に使えない。
- **各社サイトのスクレイピング** — 利用規約と著作権の両面でリスクがあるため不採用。

## どうやって「おすすめ」を決めているか

このBotは自分の興味では選びません。Yahoo!トピックス・livedoorトピックス・時事通信
ランキングという**既に人間が付けた重要度**と、報道媒体数・はてなブックマーク件数という
**外形的な指標**だけでスコアを付けます(`rank.py` の `score_cluster`)。

```
score = Σ(signal を持てば加点)
      + outlet_count の重み × (報じた媒体数 - 1)
      + hatena の重み × log10(はてなブックマーク数 + 1)
```

### レーン(総合/テック・科学)を分けている理由

**スコアはレーン内でしか比較しません。** 総合レーンとテックレーンを1つのプールに
混ぜると、`curated_yahoo` / `curated_livedoor` の項が定義上いつも0になるテック記事は
構造的に1本も選ばれなくなります(そもそもYahoo!トピックス・livedoorトピックスに
テック専用のキュレーションが存在しないため)。そのため `config.yml` で `quota` を
レーンごとに固定で分けており、`rank_and_select()` もレーンごとに独立して候補を集め・
足切りし・並べ替えています。この前提を壊す実装(全レーンを1つのリストにまとめてから
まとめて上位N件を採る、など)はしないでください。

## 名寄せについて

同じ話題を複数媒体が報じたとき、見出しを正規化して文字bigram集合を作り、
**Jaccard係数ではなく重なり係数(Szymkiewicz-Simpson, `|A∩B| / min(|A|,|B|)`)**
で類似度を測っています(`src/cluster.py` の `overlap_coefficient()`)。

理由は見出しの長さの構造的な違いです。Yahoo!トピックスの見出しは13〜16字に固定
されている(いわゆる13文字ルール)のに対し、朝日新聞やITmediaの見出しは23〜54字
あります。Jaccardは分母が和集合なので、短い見出しはどれだけ内容が一致していても
構造的に高いスコアを出せません。2026-08-31の実データでは、正解ペア(同一話題)の
重なり係数が0.385〜0.857だったのに対し、無関係なペアの最大は0.214で、閾値0.35は
その間に十分な余裕を持って収まっています。詳しい経緯は `src/cluster.py` の
`overlap_coefficient()` のコメントを参照してください。

### 既知の限界

この指標を使っても誤マッチは残ります。同日の実データで16件のクラスタにまとまった
うち2件が誤マッチでした。誤マッチのペアは正解ペアと数値上分離できません
(誤マッチ側が0.385・0.533、正解側が0.385・0.500という具合に、閾値調整では
分離できない領域で重なっています)。実害は `outlet_count` が1つ増えてスコアが
少し上がることに限られます。代表記事と要約はどちらも同じ記事(代表記事)から
取るため、見出しと要約の内容が食い違うことはありません。

## 設定の変え方

`config.yml` がユーザーが編集する唯一のファイルです。よく触る項目は以下のとおりです。

| 項目 | 変えると何が起きるか |
|---|---|
| `lanes[].quota` | そのレーンから通知する最大本数が変わる |
| `lanes[].weights` | スコアの重み。ある項目を上げるとその要素が強く効き、選ばれやすくなる |
| `lanes[].min_score` | この点数未満のトピックは、枠が余っていても通知されなくなる |
| `lookback_hours` | 何時間前までに配信された記事を取得対象にするか |
| `cluster_threshold` | 名寄せの閾値。上げると同一話題としてまとまりにくくなり、下げると無関係な話題まで1つにまとめられるリスクが上がる |
| `summary_max_chars` | 要約の目安文字数(実際の上限はこの1.5倍。超えると末尾を切り詰めて`…`を付ける) |
| `spill_over` | あるレーンでquotaが埋まらなかったとき、余った枠をもう一方のレーンの次点で埋めるか |

調整例: 総合レーンの通知がYahoo!トピックス採用記事に寄りすぎると感じたら、
`lanes: general` の `weights.curated_yahoo` を `3.0` から下げてください。

## セットアップ

Discord側の設定(Bot作成・招待・チャンネルID取得)とGitHub Secretsへの登録手順は
[`docs/discord.md`](docs/discord.md) にまとめてあります。必要な手順の全体像は
そちらを参照してください。

必要なGitHub Secretsは以下のとおりです。

- `DISCORD_BOT_TOKEN`(必須)
- `DISCORD_CHANNEL_ID`(必須)
- `GEMINI_API_KEY`(任意 — 未設定でも通知は届くが、要約なしで見出しとリンクのみになる)
- `GEMINI_MODEL`(任意 — 未設定なら `config.yml` の `gemini_model` を使う)

## ローカルでの実行

依存パッケージをインストールします。

```bash
pip install -r requirements.txt
```

`DRY_RUN=1` を付けて実行すると、Discordへの送信・Geminiへの送信・状態ファイルの
保存を行わず、組み立てた内容をログに出すだけになります。

```bash
DRY_RUN=1 python src/main.py
```

Windows PowerShellの場合は環境変数の設定を別コマンドで行います。

```powershell
$env:DRY_RUN = "1"
```

```powershell
python src/main.py
```

## 状態ファイル

`data/seen_urls.json` は、一度通知したトピックのURLを記録し、`config.yml` の
`seen_ttl_days`(14日間)は再通知を抑制するためのファイルです。クラスタ内の
全URL(代表記事だけでなく)を記録するので、代表記事が日によって入れ替わっても
再通知されません。

**同じ日に2回実行すると、2回目はほぼ空(または大幅に件数が減った状態)になります。**
これは不具合ではなく、1回目の実行で通知した記事のURLが既報として記録されるためです。
GitHub Actions側は本番実行(dry_runでない)のあとに `data/seen_urls.json` を
自動でcommit・pushします(`.github/workflows/daily.yml` の最終ステップ)。

## 著作権・利用規約について

- RSSのリード文をそのまま貼らず、Geminiに言い換えさせてから通知しています
  (`summarize.py` のプロンプトでコピー&ペーストを明示的に禁止している)。
- 記事本文は取得していません(取得しているのはRSSのタイトルとリード文のみ)。
- 通知には必ず元記事へのリンクを付けています。
- Googleニュースのフィードはcopyright表記で用途をpersonal・non-commercialに
  限定しています。個人のDiscordサーバーへの通知はこの範囲ですが、この内容を
  Webサイトなどへ転載することはできません。

## 定期実行の有効化

`.github/workflows/daily.yml` の `cron` はコメントアウトされた状態で置いてあります。
`workflow_dispatch` の手動実行(`dry_run: true` → `dry_run: false` の順)でDiscordへの
実際の投稿まで確認してから、コメントを外して定期実行を有効にしてください。
